[[Linux 子系统汇总]]

Linux 中断子系统我会从 中断编号管理、控制器抽象、中断分发、驱动注册、上下半部 这几块讲。
首先，Linux 不直接把硬件中断号当作全局中断号使用。硬件中断号通常叫 hwirq，它只在某个中断控制器内部有意义。

Linux 内核使用的是虚拟中断号，也就是 ==`virq。

两者之间通过 irq_domain 做映射。

`hwirq -> irq_domain -> virq

比如 GIC、GPIO 中断控制器、PMIC 中断控制器都可能有自己的硬件中断号空间，所以需要 irq_domain 统一管理。

第二个核心结构是 ==`irq_desc。

它可以理解为某个 virq 的总管理对象。一个 virq 对应一个 irq_desc。
里面保存这个中断的状态、统计信息、流控 handler、底层 irq_chip 信息，以及驱动注册进来的 irqaction 链表。

>`virq
>  `↓
 >`irq_desc
 >`├── irq_data
 >`├── irq_chip
 >`├── handle_irq
 >`└── irqaction 链表
 
第三个是 ==`irq_chip。

它是中断控制器的抽象操作集，负责屏蔽、打开、确认、结束中断，以及设置触发类型。例如：

>`mask
>`unmask
>`ack
>`eoi
>`set_type

不同硬件控制器，比如 `ARM GIC、GPIO IRQ controller、PMIC IRQ controller，
会实现自己的 `irq_chip。

第四个是 ==`irqaction。

驱动调用 request_irq() 时，内核会创建一个 irqaction，里面保存驱动的中断处理函数、flags、dev_id、name 等，然后挂到对应 irq_desc->action 链表上。如果是共享中断，多个 irqaction 会挂在同一个 irq_desc 下。

比如：
`request_irq(irq, my_handler, IRQF_TRIGGER_RISING, "my_dev", dev);

对应关系是：

i`rq_desc
   `└── irqaction
          `└── my_handler
共享中断则是：

`irq_desc
   `└── irqaction A -> handler_a
          `└── irqaction B -> handler_b
          
==中断发生时，大致流程是：

>`外设产生中断
    ↓
`中断控制器收到 hwirq
    ↓
`irq_domain 映射成 virq
    ↓
`通过 virq 找到 irq_desc
    ↓
`执行 irq_desc->handle_irq
    ↓
`通过 irq_chip 做 ack/mask/eoi 等硬件操作
    ↓
`遍历 irq_desc->action 链表
    ↓
`调用驱动注册的 handler

以 ARM GIC 为例，CPU 进入异常向量后，会进入中断入口函数，然后从 GIC 读取当前中断 ID。内核根据这个硬件中断号找到对应的 Linux virq，再进入通用 IRQ 分发逻辑，最后调用驱动通过 request_irq() 注册的 handler。

中断处理函数运行在硬中断上下文，要求执行快，不能睡眠，不能做耗时操作。一般只做必要的寄存器读取、清中断、保存状态，然后把耗时工作放到底半部。

Linux 常见的下半部机制有：

>softirq
>tasklet
>workqueue
>threaded irq


现在驱动里比较常用的是 workqueue 和 threaded irq。
例如使用线程化中断：

`request_threaded_irq(
    `irq,
    `top_handler,
    `thread_handler,
    `IRQF_ONESHOT,
    `"my_dev",
    `dev
`);

这里 top_handler 在硬中断上下文执行，通常快速判断并返回 IRQ_WAKE_THREAD，然后 thread_handler 在线程上下文执行，可以睡眠，适合 I2C/SPI 访问、复杂逻辑处理等。

再补充一点触发方式。中断可以是边沿触发，也可以是电平触发：

edge rising / falling
level high / low
触发方式通常来自设备树，也可以由驱动或平台代码设置，最终会调用 irq_chip->irq_set_type() 配到底层控制器。

**总结一下，Linux 中断子系统的核心是：

>irq_domain：负责 hwirq 到 virq 的映射
>irq_desc：负责管理某个 virq 的状态和分发
>irq_chip：负责操作底层中断控制器
>irqaction：负责保存驱动注册的 handler>


如果面试中一句话概括，我会说：

==Linux 中断子系统通过 irq_domain 解决硬件中断号到 Linux 中断号的映射，通过 irq_desc 管理每个 virq 的状态和分发，通过 irq_chip 抽象不同中断控制器的硬件操作，通过 irqaction 保存驱动 request_irq 注册的处理函数，最终在中断发生时完成从硬件中断到驱动 handler 的调用。==

**上面说的中断子系统 ，流控 handler是做什么的？

流控 handler 不是驱动注册的中断处理函数，它是 IRQ core 用来决定“这个中断该按什么流程处理”的函数。
它对应 irq_desc 里的类似成员：

desc->handle_irq
常见的流控 handler 有：

>handle_level_irq()
>handle_edge_irq()
>handle_fasteoi_irq()
>handle_simple_irq()
>handle_percpu_irq()

它们解决的问题是：不同类型的中断，ack/mask/eoi 和调用驱动 handler 的顺序不一样。

比如电平触发中断：

设备一直把中断线拉高
CPU 进入中断
内核通常先 mask/ack
调用驱动 handler
驱动清设备中断源
最后 unmask
如果设备的中断源没清掉，重新 unmask 后中断会立刻再进来。

大概流程：

>`handle_level_irq()
    ↓
 `mask/ack
    ↓
` handle_irq_event()
    ↓
 `遍历 irqaction，调用驱动 handler
    ↓
 `unmask

边沿触发中断不一样。边沿触发关注的是“跳变瞬间”，如果处理期间又来了一个边沿，需要记录 pending 状态，避免丢中断。

大概流程：

>`handle_edge_irq()
    ↓
  `ack
    ↓
  `handle_irq_event()
    ↓
 如果处理期间又有 pending，再处理一次 

GIC 这类控制器常见的是  handle_fasteoi_irq()。
它的特点是中断处理完以后调用 eoi 通知控制器“这个中断处理结束”。

大概流程：

>`handle_fasteoi_irq()
    ↓
 `handle_irq_event()
    ↓
 `irq_chip->irq_eoi()

所以你可以这样理解：

`irqaction->handler 是驱动真正的业务处理函数
`desc->handle_irq 是内核 IRQ core 的调度流程函数
`irq_chip 是底层硬件操作函数集合

三者关系：

>`irq_desc
  ` |
   `|-- handle_irq        // 流控 handler：决定处理流程
   `|
   `|-- irq_data.chip     // irq_chip：负责 mask/ack/eoi 等硬件操作
   `|
   `└-- action            // irqaction：驱动注册的 handler
  
一句话：

==流控 handler 负责根据中断类型控制处理流程，比如什么时候 ack、什么时候 mask/unmask、什么时候调用驱动 handler、什么时候 eoi。

举个面试回答：

irq_desc->handle_irq 是 IRQ 子系统里的 flow handler，它不是设备驱动的中断函数，
而是内核根据中断触发类型和控制器特性设置的通用处理流程。比如电平触发会使用 handle_level_irq，
边沿触发会使用 handle_edge_irq，GIC 这类控制器常用 handle_fasteoi_irq。
它会配合 irq_chip 完成 ack、mask、unmask、eoi 等操作，然后再通过 handle_irq_event 去遍历 irqaction 链表，
调用驱动通过 request_irq 注册的 handler。
